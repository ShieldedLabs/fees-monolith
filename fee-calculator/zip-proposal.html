Terminology

This document uses the key words "SHOULD" and "MUST" as BCP 14 [1] describes. This rule applies only when these key words are in all capitals.

The character § refers to sections of the Zcash Protocol Specification. [2]

The terms "actions", "conventional fee", and "marginal fee" have the definitions that ZIP 317 gives. [4] The fields fee and nExpiryHeight of a Version 6 transaction have the definitions that ZIP 230 gives. [5]

Abstract

This ZIP defines a dynamic fee mechanism. The marginal fee is the median per-action fee that users paid in recent blocks. The mechanism starts as node and wallet policy. A later network upgrade can harden it into consensus rules. The only new on-chain metadata is the fee that the user pays.

Motivation

The price of ZEC increased quickly and is now less stable. As a result, fees increased to prices that users think are too high. A decrease of the ZIP 317 marginal fee is a short-term fix only. Each change of the marginal fee makes wallet updates necessary across the ecosystem. An automatic mechanism removes this problem and adjusts the fee to price volatility and to changes in demand.

The fee is easy to explain, stays low, and changes rarely. A user can pay a higher fee for reliable inclusion when demand increases quickly.

Privacy Implications

Fees are powers of 10. The user selects one of two fee levels (standard or priority), which adds one bit of information. A light wallet trusts its server to relay the fee. The current wallet threat model already includes this trust. [6]

Requirements

A successful design:

  • Keeps to a minimum the user information that leaks by accident.
  • Computes the conventional fee from public information only.
  • Keeps the fee approximately stable in economic value when the price of ZEC changes by large amounts.
  • Gives miners a reason to include honest transactions in blocks.
  • Makes an attack that prevents honest transactions cost more than honest users pay over the window.
  • Makes sure that miners cannot use the protocol rules to increase the fees that users pay.
  • Is compatible with the NSM contributions of ZIP 235 and the action-based accounting of ZIP 317, and keeps consensus rules stateless and simple.

Specification

Notation

This specification uses median ( S ) and mean as §7.7.3 "Difficulty Adjustment" [3] defines them. The definition is median(S) = sorted(S)[ceiling((length(S) + 1) / 2)], with 1-based indexes. If S has an even length, the median is the upper of the two middle elements.

Marginal Fee Calculation

Parameter Value Units
reorg_buffer 5 blocks
lookback_window 50 blocks
fee_floor 1000 zats per action

The value chain_tip is the height of the latest known block. The window is the blocks with heights [chain_tip - reorg_buffer - lookback_window ... chain_tip - reorg_buffer]. The sequence T contains the transactions in the window.

The per-action fee of a transaction is its fee divided by max(grace_actions, logical_actions), as in ZIP 317. [4] The sequence P contains these entries, in this order:

  1. For each transaction in T, its per-action fee, one time for each logical action of the transaction.
  2. The synthetic actions that the Synthetic Actions section defines.

The new marginal fee is a suggested value, equal to median ( P ) . The conventional fee calculation stays the same as in ZIP 317.

Rationale
  • A reorg_buffer of 5 blocks decreases the risk from chain reorganizations and keeps the data recent.
  • A lookback_window of 50 blocks is approximately one hour. The sample is large, and the fee follows changes in network conditions.
  • Outliers have a small effect on the median.
  • The median counts actions, so each fee has weight in proportion to the block space that it buys. If large transactions at the floor fill the window, a per-action median lets 180 two-action transactions increase the fee by a factor of 10 for 0.036 ZEC.

Synthetic Actions

A synthetic action has a per-action fee of fee_floor and fills one unused action slot. For each block in the window, add synthetic actions as follows:

  • If the action limit of the block binds first, add one synthetic action for each unused action slot below the action limit.
  • As a fallback, if the byte limit of the block binds first, divide the unused bytes of the block by the mean bytes per action of the real transactions in T. Round the result down. Add that number of synthetic actions.

In both cases, the number of synthetic actions is at most the number of unused action slots in the block.

Rationale

Unused capacity votes for fee_floor, so the fee increases only under real demand. The Security Analysis gives the exact condition.

New Rules

Relay policy applies these rules first. A future network upgrade can harden them into consensus rules.

  • The per-action fee MUST be at least fee_floor zats.
  • The per-action fee MUST be a power of 10.
  • The wallet MUST set nExpiryHeight so that chain_tip + reorg_buffer < nExpiryHeight < chain_tip + lookback_window + reorg_buffer .
Rationale

This expiry range limits the time that a transaction with an incorrect fee stays in the mempool.

Wallet Construction

Each user interface for transactions SHOULD let the user select one of two fees:

  • The standard fee, which is the median fee.
  • A priority fee of median_fee_per_action * priority_multiplier.

Security Analysis

N is the length of P. The window holds W = lookback_window + 1 blocks (the range includes both end heights). Each block can hold A actions.

Theorem. The marginal fee is at least X > fee_floor if and only if at least ceiling(N / 2) actions in the window pay X or more per action.

Proof. The median is the element at 1-based position ceiling((N + 1) / 2) of sorted P. That element is at least X if and only if at most ceiling((N + 1) / 2) − 1 = floor(N / 2) entries are below X. This is true if and only if at least N − floor(N / 2) = ceiling(N / 2) entries are at or above X. Synthetic entries equal fee_floor < X. As a result, all of these entries are real actions.

The theorem is true for all values of N. The cost bounds below apply when N = W × A, which is true when the action limit binds before the byte limit in every block of the window. The cap on synthetic actions keeps N ≤ W × A in all cases. When the byte limit binds first, the fallback can add fewer synthetic actions, and N and the cost bounds decrease. Bounds for that case are unknown at this time.

Corollaries (when the action limit binds).

  • To increase the fee to X, an attacker pays at least X per action on ceiling(W × A / 2) actions, minus the honest actions that already pay X. This bound is true for all combinations of transaction sizes. With the parameters above, W = 51. If A = 330, the attacker pays for 8,415 actions, or approximately 0.84 ZEC per window at X = 10,000. If NU7 (25-second blocks, ZIP 218) multiplies reorg_buffer and lookback_window by 3 to keep the same time span, then W = 151. This gives 24,915 actions, or approximately 2.5 ZEC per window.
  • Two windows for blocks that are W blocks apart contain completely different blocks. To keep the fee at X for D blocks, an attacker pays at least ceiling(D / W) times the bound.
  • A miner that fills only its own blocks must mine more than half of the blocks in the window. This miner also pays the ZIP 235 burn on each action.
