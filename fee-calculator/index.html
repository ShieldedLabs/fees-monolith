Dynamic Fees
Design Adversarial Interactions GitHub

A Zcash fee market should be simple, free-market based, and private.

Users should be able to choose to pay more or less for different classes of service — better UX for them, a stronger security budget overall. The mechanism should be deployable incrementally without waiting for a Network Upgrade, and the core consensus logic should be kept isolated from the fee system.

Private

How fees stay private

The mechanism is built to leak as little as possible about individual users — by reading only public data, collapsing fee values to discrete buckets, and keeping all wallets quoting the same number.

Reads only confirmed blocks

No mempool inspection. The recommendation is computed from data the network already publishes — running the estimator leaks nothing new.

Powers-of-10 bucketing

Continuous bidding produces fees with high entropy — a timing signal. Bucketing collapses possible quoted values to roughly five (1,000 / 10,000 / 100,000 / 1,000,000 zats per action).

A single quote per network state

All wallets reading z_getstandardfees see the same number. There is no per-wallet fee-calculation methodology to fingerprint.

Two tiers, two prices

Wallets show users a Standard option and a Priority option at 10× Standard. The set of distinguishable user choices stays small — two buckets across normal traffic.

The external audit identifies three privacy conditions still under test: bucket transitions create coordinated timing signals when the recommendation jumps from one power of ten to the next; fast-lane adoption may segment urgent users from non-urgent ones; and wallet-implementation divergence would itself become a fingerprint. These are tracked as the Privacy falsifier in the adversarial test framework.

Roadmap

Phase 1: z_getstandardfees

March – April 2026

RPC endpoint that publishes fee data from confirmed blocks. Implemented in Zebra, relayed by Zaino and lightwalletd. The result is what you see above.

Phase 2: Earthquake Tests

May – August 2026

Stress-test under adversarial conditions. Replay harness, wallet developer outreach, relay and mining policy updates. Must pass test gates E2, E3, E4, E7 from the roadmap. See What Could Break This for the scenario suite.

Phase 3: Consensus Building

September 2026 –

Feature-flagged PRs in Zebra, Zaino, and lightwalletd. ZIP advancement to "Proposed" status. Wallet integration. Policy convergence gate E1: >85% for 4 consecutive windows.

Phase 4: Extended Research

Ongoing

Monitor, iterate, run extended research gates E8–E12 covering learning robustness, collusion frontier, resource-basis ablation, and controller benchmarks.
